### #1 — Counter Signals: 20.2% Win Rate

**Area:** Signal Quality  
**Severity:** High

**Problem:**  
Contrarian (`counter`) signals have resolved with a 20.2% win rate across 94 resolved signals (19W / 75L). This is strongly negative expectancy and represents a net drag on total system performance. The contrarian logic is betting against the prevailing trend, which in a mostly-bearish market environment is consistently wrong.

| Source | Wins | Losses | Win Rate |
|---|---|---|---|
| live | 53 | 17 | 75.7% |
| scanner | 128 | 38 | 77.1% |
| backtest | 600 | 675 | 47.1% |
| **counter** | **19** | **75** | **20.2%** |

**Recommended Action:**  
Disable contrarian signal logging (`log_contrarian_signals` job) or gate it with a very strict filter (min conviction ≥ 70, only in strong regime alignment). Do not trade counter signals until win rate recovers above 45% over a 50+ sample. A separate conviction threshold config for counter signals would allow live tuning without code deploys.

### #2 — 96% NULL `regime_at_signal`

**Area:** Data Quality / Phase 18  
**Severity:** High

**Problem:**  
Phase 18 added `regime_at_signal` and `btc_price_at_signal` columns to `signal_log` to capture market context at the moment a signal fires. However, only ~20 of ~1,650 resolved signals have this populated (all recent). The historical backlog has NULL, meaning:
- The `/api/analytics/signal-outcomes/trend` regime breakdown is computed from the `market_state` fallback field, not the actual regime at signal time.
- Regime-filtered analysis is unreliable for historical data.

**Recommended Action:**  
Write a one-time backfill script that, for each signal with `regime_at_signal IS NULL`, fetches the BTC weekly close at `fired_at` and applies the EMA50 regime logic to populate the field. This is deterministic and idempotent. Priority: medium-high, as regime filtering is a key trading insight.

### #3 — Missing Daily Snapshots (04-10, 04-11)

**Area:** Data Pipeline  
**Severity:** High  
**Status:** FIXED (2026-04-11)

**Problem:**  
The worker container was down for 36.4 hours (04-09 14:26 UTC → 04-11 02:52 UTC). The `snapshot_signal_outcomes` cron job (00:05 UTC daily) missed firing for both 04-10 and 04-11. The `/api/analytics/signal-outcomes/trend` endpoint had only 1 data point, making the WinRateTrend chart non-functional.

**Resolution:**  
Manually triggered snapshot backfill for 04-10 and 04-11. Also backfilled 04-04 through 04-08 which were pre-existing gaps. Trend endpoint now serves 8 data points.

### #4 — No Startup Recovery for Missed Snapshots

**Area:** Worker Reliability  
**Severity:** High  
**Status:** FIXED (2026-04-11)

**Problem:**  
The worker startup function had gap recovery for missed 4H candle closes but no equivalent check for missed daily snapshots. Any container restart would silently leave snapshot gaps.

**Resolution:**  
Modified `snapshot_signal_outcomes()` to accept an optional `snapshot_date` parameter. Added startup logic in `worker.py` that queries the last 7 days of snapshot dates, identifies any missing, and backfills them before the first cron cycle. Committed as `4296975`.

### #5 — Oracle Frontend Still Polling (Deprecated Strategy)

**Area:** Dead Code / Performance  
**Severity:** Medium

**Problem:**  
CLAUDE.md states Oracle is "deprecated from UI, backend preserved." However, `useStrategyOracle` hook (`frontend/src/hooks/useStrategyOracle.ts`) still calls `/api/strategy/oracle/{symbol}` every 30 seconds from two active chart components:
- `frontend/src/components/features/chart/components/StrategyOraclePanel.tsx:15`
- `frontend/src/components/features/chart/components/OracleMarkers.tsx:15`

This is unnecessary API load on a deprecated strategy. The backend Oracle implementation is also deeply entangled in the screener, signal summary, and best-setups routes — it cannot be safely removed without a coordinated refactor.

**Recommended Action:**  
- Short term: Increase `refetchInterval` on `useStrategyOracle` from 30s → 5 minutes or disable it entirely if the panels are not visible/used.
- Medium term: Replace Oracle panel data with Titan equivalents, then remove the hook and backend route.
- Do NOT remove `oracle.py` until analytics screener/best-setups are decoupled from it.

### #9 — Low Paper Trading Fill Rate (33%)

**Area:** Paper Trading  
**Severity:** Medium

**Problem:**  
Of 6 position attempts, only 2 filled (DOGEUSDT, APTUSDT). 4 were CANCELLED/EXPIRED (DOGEUSDT×2, APTUSDT, BNBUSDT). LIMIT orders at tight entry levels are not filling before the review window expires.

**Recommended Action:**  
Review limit order placement logic in the orchestrator. Options: (a) use a small slippage buffer (e.g., entry ± 0.1%) for better fill probability, (b) switch to MARKET orders for paper trading since fill simulation doesn't need to be realistic, or (c) extend the fill window. Track fill rate as a KPI going forward.
