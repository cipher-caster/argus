## 3. Data Fetching Patterns

### 3.1 Missing `staleTime` — 2 hooks

- `hooks/useMarketOverview.ts:13-18` (`useMarketSummary`) — has `refetchInterval: 60000` but no `staleTime`
- `hooks/useMarketOverview.ts:24-29` (`useCoins`) — has `refetchInterval: 30000` but no `staleTime`
- `hooks/useMarketData.ts:94-100` (`useTicker`) — has `refetchInterval: 5000` but no `staleTime`

**Fix:** Add `staleTime` slightly below the refetch interval.

### 3.2 Duplicate hook — `useProvider` vs `useProviderInfo`

- `hooks/useMarketData.ts:14-19` (`useProviderInfo`) — query key `["providerInfo"]`
- `hooks/useMarketData.ts:106-111` (`useProvider`) — query key `["provider"]`

Same endpoint, different cache keys. Remove `useProvider`.

### 3.3 No `onError` callbacks in mutations — 4+ instances

- `hooks/useTradingData.ts:76-80` (`useUpdateTradingConfig`)
- `hooks/useTradingData.ts:87-90` (`useClosePosition`)
- `hooks/useTradingData.ts:97-100` (`useCloseAllPositions`)
- `hooks/useTradingData.ts:107-111` (`usePauseTrading`)
- `hooks/useAnalyticsData.ts:106-112` (`useUpdateSignalLogConfig`)

Mutation errors are silently swallowed — no UI feedback on failure.

### 3.4 No optimistic updates — zero mutations implement this

All trading mutations wait for server round-trip before updating UI. Users see stale state for 500ms–2s after close/config actions.

- `useUpdateTradingConfig` — should optimistically update `["trading", "config"]`
- `useClosePosition` — should optimistically remove from `["trading", "positions"]`
- `useUpdateSignalLogConfig` — should optimistically update signal log config

### 3.5 Overly broad cache invalidation

- `hooks/useMarketData.ts:31` (`useSetProvider`) calls `qc.invalidateQueries()` with no key — invalidates **all** queries in cache.

**Fix:** Scope to `["providerInfo"]`, `["ohlcv"]`, `["tickers"]`, `["symbols"]`.

### 3.6 Inline data transformation in component

- `components/features/dashboard/DashboardStatusBar.tsx:30-38` — Filters best setups by regime inline. Should be a `useAlignedSetups(regimeType)` hook.

## 5. Performance Issues

### 5.1 Zustand store over-subscription — `DrawingCanvas.tsx`

`DrawingCanvas.tsx:21-35` subscribes to 15 separate store slices. Any state change re-renders the entire canvas.

**Fix:** Collapse into a single `useDrawingStore(selector)` call with shallow comparison.

### 5.2 Inline sort without `useMemo` — 3 files

- `StatsCards.tsx:28-32` — sorts `coins` array for top gainer/loser/volume on every render
- `OracleMarkers.tsx:20-33` — builds and sorts markers on every render
- `BacktestPerformance.tsx:189` — spreads and sorts coins array on every render

**Fix:** Wrap each in `useMemo(() => ..., [dependency])`.

### 5.3 Inline computation without `useMemo`

- `MarketSentimentBar.tsx:109-149` — IIFE signal parser runs on every render
- `OracleScreener.tsx:27` — `.filter()` on every render including keystroke
- `WatchlistPanel.tsx:112-120` — drag sensors recreated on every render

### 5.4 Full Zustand store subscription

`WatchlistPanel.tsx:87` destructures entire `useWatchlistStore()` object. Any store field change triggers re-render.

**Fix:** Use individual selectors: `const items = useWatchlistStore(s => s.items)`.

### 5.5 `CoinTable` memo defeated by parent

`CoinTable.tsx:207` is wrapped with `memo()` but parent passes unstabilised `onSort` callbacks and array references. Parent must use `useCallback`/`useMemo` on these props.

### 5.6 Sparkline generated per row

`CoinTable.tsx:192` — `generateDeterministicSparkline()` called inline for every row on every render as fallback. Should be memoized per coin.

### 5.7 Constant arrays in render

`SignalLog.tsx:211-215` — inline `[{...}, {...}, ...]` array literal for market gate toggles. Extract as module-level constant.

## 6. API Lib Layer

### 6.1 Inconsistent `apiFetch` usage

`lib/apiClient.ts` defines a centralized `apiFetch<T>()` wrapper (uniform error handling, consistent base URL). Only 3 of 38 API functions use it:

- `api.ts:283` (`fetchRegime`) ✓
- `marketApi.ts:59-66` (`fetchMarketSummary`, `fetchTickers`) ✓

The remaining 28+ functions use bare `fetch()` with manual per-function `if (!response.ok) throw new Error(...)` — inconsistent error message format and duplicated boilerplate.

**Fix:** Migrate all API functions to `apiFetch<T>()`.

### 6.2 Error message format inconsistency

Two error patterns coexist:
- Pattern A (older): `throw new Error(`Failed to fetch OHLCV: ${response.statusText}`)` — includes HTTP status
- Pattern B (newer): `throw new Error("Failed to fetch best setups")` — no status

Centralising on `apiFetch` resolves this automatically.

### 6.3 Optimization API endpoints not exposed

Backend exposes at `/api/optimization/`:
- `GET /experiments`
- `GET /experiments/{id}`
- `GET /best`
- `POST /apply`
- `GET /api/trading/trade-analysis`
- `GET /api/trading/recommendations`

None of these have corresponding functions in `lib/`. Optimization features are frontend-inaccessible.

### 6.4 Unused API function

`lib/api.ts:606` — `fetchPositionDetail(id)` defined but never imported anywhere.

**Fix:** Remove or wire up to position detail modal.

### 6.5 No schema sync mechanism

Backend Pydantic models and frontend TypeScript interfaces are maintained manually with no OpenAPI codegen. Types are currently in sync but will drift over time.
